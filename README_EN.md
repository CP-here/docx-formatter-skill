# docx-formatter — Professional Chinese Word Formatting Skill

[中文](README.md) | English

docx-formatter formats text or Markdown content into professional Chinese Word documents. Its most common use is to lay out AI-generated Markdown prose (reports, documentation, proposals, papers, lecture notes, etc.) as .docx files following academic and engineering conventions, supplementing it with library functions for constructs that Markdown cannot express; it covers the complete formatting chain of section structure, body text, mathematical formulas, tables, flowcharts, tables of contents, citation superscripts, and document validation, producing .docx files that meet academic and engineering standards. For the formatting results, see [README.docx](README.docx) and [README.pdf](README.pdf) in the repository.

![Skill effect overview](assets/effect-overview.png)

*Figure: On the left is the README.md source; on the right is the README.docx generated from the same content by this skill.*

The skill uses a single-engine architecture and depends only on Python 3.8 or later and python-docx. Mathematical formulas are generated by omml_math_kit.py as OMML XML directly — Word's native formula format — so formulas remain editable in Word, with no need for Node.js or any external conversion tool.

## Getting Started

This skill is a function library with no executable entry point: docx_layout_kit.py has no main() function, and running it directly produces no output. An agent generates documents by writing a calling script that imports the library functions and calls them in order according to the document structure.

Before generating a document, an agent should first read scripts/_build_readme_docx.py. This file is the standard skeleton for the skill, demonstrating the complete calling sequence from setup_document() to doc.save() in its own body; it is also used to generate the README.docx in the project root, so it always stays in sync with the library.

| Reference File | Purpose |
| --- | --- |
| scripts/_build_readme_docx.py | Standard skeleton example, covering the complete calling sequence for cover, table of contents, headings, body text, bullet paragraphs, formulas, data tables, flowcharts, captions, and bibliography |
| SKILL.md | Complete parameter documentation, formatting values, rules, and pitfalls for each function |
| scripts/docx_layout_kit.py | The function library itself and its preset values, used to confirm implementation details |

The standard workflow is: the agent reads the import section and calling sequence of _build_readme_docx.py, copies docx_layout_kit.py into the working directory (adding omml_math_kit.py and formula_templates.py if the document contains formulas), creates a new calling script and writes the content in the order shown by the example, then validates with docx_validator.py after running it.

## Core Modules

### Standard Formatting

Headings use SimHei and body text uses SimSun. The document title is 26pt (No. 1), centered and bold; level-1 headings are 16pt (No. 3), left-aligned; level-2 and level-3 headings are 12pt (Small 4). Body text is 12pt (Small 4), justified, with a 2-character first-line indent and 1.5 line spacing throughout. The paper size is A4, with margins of 2.54cm top and bottom and 3.18cm left and right. Page numbering is tiered: the cover and table of contents show no page numbers, the body starts at page 1, and the footer contains a centered PAGE field in 10.5pt (No. 5) Times New Roman. The centered title block on the cover page is positioned by top whitespace, whose height is converted from a ratio of the text area height and automatically scales proportionally when the paper or margins change. The font, size, boldness, and black color of each heading level are all written into Word's built-in Heading styles; the heading text itself carries no direct character formatting. This both overrides the styles' default blue color and template theme font references, and prevents Word from copying heading fonts into entries when updating the TOC field, so TOC entries render strictly according to the styles. CJK/Latin font separation: Latin text in body copy uses the Times New Roman serif face and Latin text in headings uses the Arial sans-serif face, aligning with the font family design of NJUThesis.

| Function | Purpose |
| --- | --- |
| setup_document | Create a document and apply page settings, automatically resetting the figure/table counters |
| add_cover_page | Cover page with a centered title block positioned by top whitespace, forming its own section with no page number |
| add_title | Document main title when no cover is used, 16pt (No. 3) SimHei, centered and bold |
| add_h1, add_h2, add_h3 | Level-1, level-2, and level-3 headings using Word's built-in Heading styles, able to appear in the table of contents |
| add_body | Body paragraph, supporting bold markers and citation superscripts |
| add_item_para | Paragraph with a bold label plus bulleted content, with the entire label bolded |

```python
from docx_layout_kit import setup_document, add_title, add_h1, add_body

doc = setup_document()
add_title(doc, "信号分析实验报告")
add_h1(doc, "一、实验目的")
add_body(doc, "本实验验证傅里叶分析方法在周期信号处理中的有效性。")
```

### Formatting Presets

Formatting parameters are centralized in the PRESETS dictionary at the top of docx_layout_kit.py, managed in groups for headings, body text, bullets, captions, page, table of contents, cover, and so on. Each formatting function uniformly reads the currently active preset.

- set_preset switches the entire set of formatting parameters and must be called before setup_document; the default preset matches the standard formatting
- Adding a new preset requires only appending a nested dictionary of the same structure to PRESETS
- CJK/Latin font separation is supported; when enabled, Latin text uses Times New Roman while Chinese fonts remain unchanged
- The cover whitespace ratio lives in the cover group of the preset; the whitespace height is derived by multiplying it by the text area height, so the cover position scales proportionally when the paper and margins change

### OMML Math Formulas

The formula builder provides a set of composition functions that generate OMML XML directly and insert it into the document; the result is a natively editable Word formula, identical to one inserted by hand. For complex structures such as fractions nested in fractions, double summations, or nested functions, the builder functions can be combined freely.

| Builder Function | Purpose |
| --- | --- |
| r | Plain mathematical text, automatically escaping XML special characters |
| sub | Subscript, e.g. k as a subscript of a |
| sup | Superscript, e.g. x squared |
| frac | Fraction |
| sumOp | Summation sign, using a subscript structure with the Unicode ∑ to avoid abnormal rendering of empty superscripts |
| func | Function name with arguments, e.g. cos and exp |
| paren | Parenthesis structure |
| bracket | Bracket structure |
| math | Display formula, centered on its own line |
| inlineMath | Inline formula, mixed with body text |

A display formula, using the Fourier series as an example:

```python
from docx_layout_kit import add_eq_para
from omml_math_kit import r, sub, frac, sumOp, func, math

add_eq_para(doc, math([
    r("f(t) = "),
    frac([sub("a", "0")], [r("2")]),
    r(" + "),
    sumOp([r("k")], [sub("a", "k"), func("cos", [r("k"), r("ωt")])]),
]))
```

The result is a natively editable Word formula (Markdown cannot render OMML; the line below is a plain-text approximation, not input syntax; for the actual rendering, see [README.docx](README.docx) in the repository):

> f(t) = a₀/2 + Σₖ aₖ cos(kωt)

An inline formula mixed with body text:

```python
from docx_layout_kit import add_body_with_math
from omml_math_kit import sub, inlineMath

add_body_with_math(doc, [
    ("text", "其中，"),
    ("math", inlineMath([sub("a", "k")])),
    ("text", "为傅里叶系数，其数值由欧拉公式确定。"),
])
```

formula_templates.py includes several commonly used formula templates — ready-made OMML formula objects that can be imported and inserted into a document without reassembling the builder functions, and that can also serve as reference patterns for custom formulas. Greek letters and mathematical symbols are written directly as Unicode, such as λ, τ, α, β, ∑, ×, ·, ∈.

The summation sign must be built with sumOp. If a summation uses an n-ary operator with an empty superscript, Word renders an invisible superscript placeholder box, making the file appear corrupted; sumOp instead uses a subscript structure with the Unicode ∑, completely avoiding the problem. All functions that accept child elements automatically flatten nested lists internally to prevent XML concatenation errors.

### Citation Superscripts

Reference markers in body text are rendered automatically as superscripts, applicable to add_body and add_item_para, in three formats:

| Format | Example |
| --- | --- |
| Single citation | [1] |
| Multiple citations | [1,2] or [1, 2] |
| Range citation | [1-3] |

```python
add_body(doc, "傅里叶分析方法在信号处理任务中表现出色[1]。后续研究[2,3]进一步验证了这一结论。")
```

### Bibliography List

add_bibliography generates a GB/T 7714-2015 numeric bibliography, formatted to align with the NJUThesis LaTeX template and paired with the citation superscripts in the body: [1] in the body points to the first item in the list, and so on.

- Section heading: 16pt (No. 3) SimHei, bold and centered, using the Heading 1 style, appearing in the table of contents
- Entries: 10.5pt (No. 5) SimSun, justified, 1.5 line spacing, with a 2-character hanging indent so that wrapped lines align with the text after the number
- Numbering: [1], [2], and so on are generated automatically in the order passed in, with no manual writing needed

```python
add_bibliography(doc, [
    "张三, 李四. 示例期刊论文题名[J]. 示例期刊, 2020, 12(3): 45-56",
    "王五. 示例图书题名[M]. 示例市: 示例出版社, 2019",
    "赵六. 示例学位论文题名[D]. 示例市: 示例大学, 2021",
    "钱七. 示例会议论文题名[C]//示例会议论文集. 示例市: 示例出版社, 2022: 78-85",
    "示例标准化技术委员会. 示例标准题名: 示例标准编号[S]. 示例市: 示例出版社, 2018",
    "孙八. 示例网页题名[EB/OL]. (2023-01-01)[2023-06-05]. https://example.com",
])
```

Entries are organized by document type and are passed in without numbers: journals are marked [J], books [M], conference papers [C], dissertations [D], standards [S], and electronic resources [EB/OL] with an update date and access path. Multiple authors are separated by commas; for three or more authors, take the first three and append "等" or "et al". The section heading defaults to "参考文献" and can be customized via the title parameter.

### Tables, Boxes, Flowcharts

Flowcharts are built from Word tables and Unicode arrows, without images or emoji, so the result remains editable in any version of Word. A vertical flowchart is formed by stacking horizontal arrow rows and downward arrows alternately; using a signal processing flow as an example:

```python
add_arrow_row(doc, "① 时域采样", "离散信号 x(n)")
add_arrow_down(doc)
add_arrow_row(doc, "② 加窗处理", "加窗信号")
add_arrow_down(doc)
add_arrow_row(doc, "③ 离散傅里叶变换", "频谱 X(k)", left_shade="D9D9D9")
add_arrow_down(doc)
add_arrow_row(doc, "④ 频谱分析", "特征向量", left_shade="D9D9D9")
add_arrow_down(doc)
add_separator_note(doc, "----- 信号预处理止于此处，后续由分类器承接 -----")
add_arrow_down(doc)
add_box(doc, "分类决策：特征归一化 / 模式匹配 / 结果输出")
add_fig_caption(doc, "信号处理与分类流程图")
```

Component functions:

| Function | Purpose |
| --- | --- |
| add_box | Single centered box |
| add_multi_line_box | Multi-line text box |
| add_multi_col_table | Row of side-by-side boxes |
| add_arrow_down | Centered downward arrow connecting the boxes above and below |
| add_arrow_horizontal | Standalone centered horizontal arrow |
| add_arrow_row | Horizontal arrow row, expressing a transformation from process to output |
| add_separator_note | Centered dashed separator note |

Side-by-side boxes express parallel branches of equal standing, while multi-line boxes hold multi-line text; the horizontal arrow is a standalone centered arrow on its own line, not bound to any table, used to express a before-and-after relationship within the same row.

The horizontal arrow row is a signature construct of this skill. It is implemented as a 3-column table with equal left and right widths under a locked fixed layout, so the arrow always sits at the exact geometric center of the table regardless of how long the text on either side is; once the vertical lines in the middle merge, the left and right cells become visually connected. The fixed layout also guarantees that column widths do not reflow when pages break, when zooming, or when the file is opened in a different version of Word. When the two sides are of equal standing, no shading is applied; when they are at different levels, the left_shade parameter can be passed to produce a gray-left, white-right effect, used to express a level transition such as that from a preprocessing stage to a decision stage.

### Layered Architecture Diagrams

add_layered_architecture expresses a multi-layer architecture through stacked table boxes, allowing full-width layers and side-by-side layers to be mixed, with spacer paragraphs inserted automatically between layers. Using a signal processing system as an example:

```python
add_layered_architecture(doc, [
    ["采集层：传感器阵列 / 信号调理 / 抗混叠滤波"],
    ["预处理层：去直流 / 滤波 / 加窗"],
    [["变换模块", "快速傅里叶变换"],
     ["分析模块", "频带能量 / 谱质心"],
     ["决策模块", "模式匹配 / 阈值判断"]],
    ["应用层：频谱显示 / 报告输出"],
], col_widths=[4.0, 5.0, 5.0])
```

The first line of every box in both full-width and side-by-side layers is a bold name. The overall diagram width has only one source: when col_widths is passed, its sum is the total width, and full-width layers and side-by-side layers share the same total width (the boxes above and below are necessarily equal in width); when only width_cm is passed (14cm by default), it is the total width, and side-by-side layers divide it evenly.

### Automatic Figure/Table Numbering

Figure and table captions are numbered automatically by internal counters, with no manual entry needed. Figure captions go below the figure and table captions above the table; the two numbering sequences are independent of each other.

```python
add_box(doc, "系统架构")
add_fig_caption(doc, "信号处理系统架构")    # 自动生成 图1 信号处理系统架构

add_table_caption(doc, "参数对比")          # 自动生成 表1 参数对比
add_data_table(doc, headers, rows, col_widths)
```

setup_document calls reset_counters automatically, so every generated document starts from Figure 1 and Table 1. Passing an empty string to add_fig_caption generates a pure spacing paragraph without incrementing the counter. add_note adds a centered italic note below a figure.

### Code Blocks and Data Tables

add_code_block renders code content in the Consolas monospace font, 9pt by default, with light gray shading, no first-line indent, and one paragraph per line:

```python
add_code_block(doc, "python docx_validator.py output.docx --verbose")
```

add_data_table generates a data table with a gray header in bold centered SimHei, fixed column widths, with the last column of data rows left-aligned and the rest centered:

```python
add_table_caption(doc, "排版标准")
add_data_table(doc,
    ["元素", "字体", "字号"],
    [
        ("文档标题", "黑体", "三号 16pt"),
        ("正文", "宋体", "小四 12pt"),
    ],
    col_widths=[2.2, 1.8, 2.0])
```

add_math_to_cell inserts an inline OMML formula into a table cell, suitable for scenarios such as comparing a function call with its rendered result:

```python
from omml_math_kit import sub, inlineMath

table = add_data_table(doc, ["元素", "调用", "效果"], rows, col_widths=[2.0, 6.0, 5.0])
add_math_to_cell(table.cell(1, 2), inlineMath([sub("X", "k")]))
```

The helper functions set_table_border and set_cell_shading control table borders and cell shading respectively.

### Cover Page

The cover page is generated on demand, not inserted by default, and is produced by add_cover_page, which must be called before writing any other content. The cover is a centered title block: the main title is 26pt SimHei, the subtitle 20pt SimHei, and the organization and date 15pt SimSun, all of which except the main title may be omitted — if omitted, that line is not generated.

```python
doc = setup_document()
add_cover_page(doc, "文档标题", subtitle="技术方案",
               org="某某科技有限公司", date="2026年9月")
add_toc(doc)
add_h1(doc, "一、概述")
```

The title block is positioned with top whitespace rather than vertical centering: the block sits a proportionally calculated distance from the top of the text area, and the whitespace below extends naturally. The default whitespace ratio is 0.264, which on A4 paper gives 6.50cm of whitespace and places the start of the main title paragraph about 9.04cm from the top of the page (30.4% of the page height); for a cover with fewer lines, the top edge of the main title stays in place and the whitespace below is naturally larger. The whitespace height is not hard-coded as a number of lines; instead, the text area height is first computed from the paper height and the top and bottom margins, then multiplied by the cover whitespace ratio and converted into a number of blank paragraphs with fixed line spacing, with any remainder shorter than one paragraph attached to the space before the main title paragraph. As a result, when the paper is changed, the margins are altered, or the entire preset is switched, the cover position scales proportionally and automatically, with no manual adjustment needed. The blank whitespace paragraphs use fixed line spacing, so each paragraph's height is exactly the set value and the total whitespace deviates from the target by far less than 1 point. The whitespace ratio has an upper limit of 0.5; exceeding half the text area pushes the title block onto the second page.

The cover forms its own section and shows no page number; the table of contents section that follows likewise shows no page number, and the body starts at page 1. Once a cover is used, add_title need not be called again. The whitespace consists of empty paragraphs and renders normally in Word and WPS; if the delivery chain passes through a docx-to-HTML converter that strips empty paragraphs, the whitespace may be lost.

### Table of Contents Generation

The table of contents is generated on demand, not inserted by default. The heading functions use Word's built-in Heading styles, and add_toc inserts a TOC field after the cover and before the body; holding Ctrl and clicking an entry in Word jumps to the corresponding heading. When Word opens the document it prompts to update fields, and choosing "Yes" generates the TOC entries; the entries are computed by the field when Word updates it, and placeholder text is shown before updating.

```python
doc = setup_document()
add_title(doc, "实验报告")
add_toc(doc)
add_h1(doc, "一、概述")
add_body(doc, "正文内容")
```

The TOC title is 16pt (No. 3) centered SimHei. Within the TOC, chapter title lines use 12pt (Small 4) SimHei, level-1 and level-2 section title lines use 12pt (Small 4) SimSun, and line spacing is a uniform fixed 20pt; chapter title lines have 6pt before and 0pt after and are written flush left, level-1 section title lines are indented by 1 Chinese character, and level-2 section title lines by 2 Chinese characters, with 0pt before and after for both kinds of section title lines. The three kinds of entries correspond in turn to the document's level-1, level-2, and level-3 headings. The default levels are 1 through 3; passing the levels parameter can include only level 1 and 2, and the document main title never enters the table of contents. By default, TOC entries are generated when Word opens the document and prompts to update fields, implemented via the w:updateFields switch in the document settings; passing auto_update=False disables this behavior, requiring a manual update by right-clicking the TOC and choosing to update the field. The end of the table of contents is a section break, separating it from the body and triggering body page numbering to start at 1. TOC entry fonts render strictly according to the formats above: chapter title lines in SimHei, level-1 and level-2 section title lines in SimSun. When Word updates the TOC field it copies the direct character formatting of the heading text into the entries, but this skill's headings never set fonts on the text and instead write character formatting only into the Heading styles, so Word has nothing to override and entry fonts are not dragged along by the headings' SimHei.

### Page Numbers

The cover page and the table of contents page show no page numbers, and numbering starts at 1 on the first page of the body. A single-section document with no cover and no TOC needs no handling, since setup_document already numbers pages consecutively from page 1; a document containing a table of contents is sectioned automatically by add_toc with no extra call needed; for a document with a cover but no table of contents, start_body must be called manually before the first body heading.

```python
doc = setup_document()
add_cover_page(doc, "实验报告")   # 封面页，不显示页码
start_body(doc)                  # 正文另起一页
add_h1(doc, "一、概述")           # 页码为 1
add_body(doc, "正文内容")
```

start_body clears the footers of all preceding sections (the cover and the table of contents each form their own section, so both are cleared), so that neither shows page numbers; it then creates a new section whose page parameters follow the preset, with a next-page section break, so it also serves as the page break between the cover or TOC and the body — do not add another page break. The body section sets the page number start value to the preset page.body_page_start via w:pgNumType, which defaults to 1, and the footer continues to use a centered PAGE field in 10.5pt (No. 5) Times New Roman. Calling start_body repeatedly does not create additional sections; from the second call onward it is a no-op. When the cover ends with a section break, the last section is still empty, in which case start_body directly reuses that section as the body section instead of creating a new one, and add_toc likewise skips its own leading page break; together the two avoid producing an extra blank page.

### Lightweight Document Validation

docx_validator.py is implemented on the pure Python standard library with no external dependencies, and runs 5 structural checks after a document is generated:

| Check | Description |
| --- | --- |
| ZIP integrity | All ZIP entries can be extracted |
| XML well-formedness | All XML and relationship files can be parsed |
| File reference integrity | Every target in the relationship files exists within the package |
| Content type declarations | All XML files in the package have content type declarations |
| Whitespace preservation | Text nodes with leading or trailing whitespace carry the preservation attribute |

```bash
python docx_validator.py output.docx --verbose
```

The exit code is 0 when all checks pass, and 1 otherwise.

### Safe Extraction and Repacking

safe_extract rejects symbolic links and validates path boundaries when extracting .docx files, preventing path traversal attacks; rezip repacks a directory into a .docx file, ensuring [Content_Types].xml is stored first and written atomically to the target file. Together they form the safe foundation for editing existing documents.

## Optional Modules

The following modules are not enabled by default, do not check the environment, and do not install dependencies; they are used only when the corresponding functionality is explicitly requested.

### PDF Rendering Validation

Convert the generated .docx to PDF for visual inspection. Two paths are available, chosen by platform:

| Path | Dependency | Applicable Platform | Script |
| --- | --- | --- | --- |
| Windows Word (preferred on Windows) | Microsoft Word + `pip install pywin32` | Windows | `scripts/optional/office/word2pdf.py` |
| LibreOffice | LibreOffice (`soffice` command line) | Cross-platform | `scripts/optional/office/soffice.py` |

On Windows with Word installed locally, the Word path is preferred. This path uses Word's own layout engine, so Chinese fonts, OMML formulas, TOC fields, and footer page numbering sections all match opening the document in Word, making it closer to real Word rendering than LibreOffice. Fields are updated before export so the table of contents does not retain placeholder text; each export uses a separate Word instance with the document opened read-only, and the document is closed and the instance quit afterward, without disturbing Word windows the user already has open or leaving behind stray WINWORD.EXE processes.

```bash
# Windows：默认输出到源文件同目录同名（output.docx → output.pdf）
python scripts/optional/office/word2pdf.py output.docx

# 指定输出文件或输出目录
python scripts/optional/office/word2pdf.py output.docx -o dist/output.pdf
python scripts/optional/office/word2pdf.py output.docx --outdir ./pdf_out

# 导出 PDF/A-1b
python scripts/optional/office/word2pdf.py output.docx --pdfa
```

On other platforms, or when using LibreOffice:

```bash
python scripts/optional/office/soffice.py convert output.docx --outdir ./pdf_out
```

### XSD Schema Validation

Perform in-depth OOXML schema validation on the XML parts inside a .docx file. This is stricter than the lightweight validation and depends on lxml:

```bash
python scripts/optional/office/validate.py output.docx
```

### Editing Existing Documents

Modify the content of an existing .docx file with a workflow of safe extraction, merging fragmented runs, editing XML, repacking, and validating:

```python
from docx_layout_kit import safe_extract, rezip
import zipfile

with zipfile.ZipFile("input.docx", "r") as zf:
    safe_extract(zf, "./unpacked")

# 编辑 XML 后重新打包
rezip("./unpacked", "output.docx")
```

### Tracked Changes and Comments

accept_changes.py accepts all tracked changes in a document through a LibreOffice macro; comment.py manages comments, maintaining a cross-link system across 6 comment-related files, with comment XML templates located in scripts/optional/templates.

## Formatting Standards

| Element | Font | Size | Style | Space Before | Space After |
| --- | --- | --- | --- | --- | --- |
| Document Title | SimHei | 26pt (No. 1) | Bold, centered | 24pt | 18pt |
| Level-1 Heading | SimHei | 16pt (No. 3) | Bold, left-aligned | 24pt | 6pt |
| Level-2 Heading | SimHei | 12pt (Small 4) | Bold, left-aligned | 12pt | 6pt |

The page is A4, with margins of 2.54cm top and bottom and 3.18cm left and right, and 1.5 line spacing for body text. A page number is centered in the footer in 10.5pt (No. 5) Times New Roman, automatically numbered by a PAGE field; when a cover or table of contents is present, the front matter shows no page numbers and the body starts at page 1. The cover title block is positioned with top whitespace, whose height is converted from a ratio of the text area height, scaling proportionally and automatically when the paper or margins change. CJK/Latin font separation: Latin text in body copy uses the Times New Roman serif face and Latin text in headings uses the Arial sans-serif face. The spacing system aligns with the NJUThesis LaTeX template, whose global line spacing multiple is 1.625, matching the visual effect of Word's 1.5 line spacing.

## Environment Requirements

There are only two required dependencies, Python 3.8 or later and python-docx:

```bash
pip install python-docx
```

Optional dependencies are installed as needed: pywin32 for rendering PDFs on Windows (together with local Word), LibreOffice for PDF rendering on non-Windows platforms and for accepting tracked changes, lxml for XSD schema validation, Poppler's pdftoppm for PDF-to-image inspection, and pandoc for reading the content of existing documents.

## Installation

### Option 1: `npx skills` (Recommended)

```bash
npx skills add https://github.com/CP-here/docx-formatter-skill --skill docx-formatter
```

### Option 2: Copy into the Project Directory (Travels with the Repository)

If you want every AI assistant within a project to follow this skill's formatting rules, copy the `docx-formatter/` directory into that project's skills directory, keeping the directory name consistent with the name field in SKILL.md:

| Client | Project-level Path |
| --- | --- |
| Claude Code | `<project>/.claude/skills/docx-formatter/` |
| Codex | `<project>/.codex/skills/docx-formatter/` |
| Cursor | `<project>/.cursor/skills/docx-formatter/` |
| WorkBuddy | `<project>/.workbuddy/skills/docx-formatter/` |
| Other frameworks | Any location under `<project>` where the assistant can discover `SKILL.md` (must be inside the project folder) |

The advantage of the project level is that the skill travels with the repository, so after committing, anyone who opens the project automatically gains this formatting capability.

### Option 3: Copy into the User-level Skills Directory

Copy into the current user's skills directory for use across all projects:

| Client | User-level Path |
| --- | --- |
| Claude Code | `~/.claude/skills/docx-formatter/` |
| Codex | `~/.codex/skills/docx-formatter/` |
| Cursor | `~/.cursor/skills/docx-formatter/` |
| WorkBuddy | `~/.workbuddy/skills/docx-formatter/` |
| Other frameworks | Any location under the current user's home directory where the assistant can discover `SKILL.md` |

The advantage of the user level is that all of the current user's projects can use it without copying it project by project; after installation, reference the skill in conversation with a slash, for example `/docx-formatter`.

After installation, restart the assistant session so the skill index refreshes.

## Usage

After installation, simply describe your needs in conversation to trigger the skill:

- Format this content as Word
- Convert this Markdown into a Word document
- Generate a Word document with formulas
- Format a technical report as Word
- Format this document with mathematical equations
- Create a flowchart in Word

Optional features must be explicitly requested, such as converting a document to PDF to check the result, adding comments to a document, or modifying an existing document by way of tracked changes.
